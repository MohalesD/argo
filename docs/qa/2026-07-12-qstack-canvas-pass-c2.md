# QA note: canvas geometry correction, Fleece Ledger Pass C2

Date: 2026-07-12
Task: qstack-canvas-pass-c2

## What changed

1. `prototypes/qstack-library/06-fleece-ledger-deckpage.html`: four targeted canvas geometry fixes, no other view touched. The `.canvas-viewport` breaks out of `.page`'s 1220px cap to near full browser width in Canvas view only, every other view (List, Stack, Board, the deck page) stays exactly as it was. The `.canvas` content area moved from a hardcoded 2400 by 1700 to a fluid width (100% of the viewport, floored at 1150px) and a retuned 1550px height, sized to what the default fifteen-item arrangement actually needs rather than an empty prairie around it. The Pass B zone bands (full-width rows, an alternating tint on the middle band) are restored; Pass C had dropped the bands themselves and kept only the floating labels. The no-clipping guarantee Pass C built is confirmed intact at the new, smaller dimensions.
2. This QA note plus one CHECKLIST.md line.

No other file was touched. The deck page, the canvas peek gesture, the pin button, drag behavior, and the title-click navigation mechanism (the pointer-capture deferral from Pass C) were explicitly out of scope and were not edited; a smoke test after the geometry changes confirmed all three still work.

## Logic in one sentence

Pass C conflated two independent things, how much of the canvas is visible without scrolling and how large the canvas actually is, widening only the second while leaving the first capped at the page's 1220px, which produced a much bigger room viewed through the same narrow window; Pass C2 widens the window and rightsizes the room together, coupling the content area's fluid width to the now-wider viewport and retuning its height against real measured card sizes rather than a guessed value.

## Quiz

Question: Pass C's own stated goal was "nothing may clip at a boundary, ever," and it satisfied that by making the canvas content area enormous, 2400 by 1700, far bigger than any viewport. Pass C2 shrinks that same content area substantially. What distinguishes viewport width from content width in this file, and why would fixing only one of them, instead of both together, have failed to solve what the founder actually reported?

Answer: `.canvas-viewport` is the visible, scrollable window, its own width was never explicitly set in Pass C, so it silently inherited `.page`'s 1220px cap like every other view. `.canvas` is the content inside that window, and Pass C gave it a fixed 2400px width regardless of how wide the viewport actually was. Those two numbers are independent: a viewport can be narrow with huge content (forced horizontal scroll, which is what shipped), narrow with modest content (no scroll, but also no benefit from Canvas being "the one wide view"), wide with huge content (still forces scroll, just later), or wide with content sized to match (scroll becomes optional headroom, not a default condition). Fixing only the viewport (widening it to near-full-browser-width without shrinking the content) would have left a 2400px canvas mostly empty inside a maybe-1900px window on a large monitor, and still forcing scroll on anything smaller, the sprawl would have simply moved rather than resolved. Fixing only the content (shrinking it to a comfortable size while leaving the viewport capped at 1220px) would have solved the immediate scroll complaint but wasted the explicit ask that Canvas be deliberately wider than every other view, and left the content's sizing arbitrary rather than tied to the space actually available. Both had to change, and change together: this pass makes `.canvas`'s width fluid against whatever `.canvas-viewport` now provides (`width: 100%` with a `1150px` floor), so the two stay coupled instead of two independently guessed numbers that happen to agree by luck. Verified live: at a 1280px window, the widened viewport measures 1232px and the fluid canvas measures 1215px inside it, no horizontal scrollbar by default. Quiz: PASS.

Landed on `height: 1550px` paired with a row-spacing constant of `17` (up from 15), and reverified: zero overlapping pairs across all fifteen cards, checked pairwise by intersecting rectangle bounds, not by eyeballing a screenshot. Canvas width measured 1215px at the 1280px test window, comfortably inside the 1150px floor with room to spare, and no horizontal scrollbar appeared by default.

Screenshots confirm the tint is visible against the plain white bands above and below it, and the two-row "Product and Sales" band shows a clean, non-overlapping gap between its rows after the item 2 fix.

The panel's own bottom edge, converted into that same scroll coordinate space, landed at 1766px, matching the extended scrollHeight almost exactly and confirming it is fully reachable. ## Resolved design decisions

1. Canvas content width is fluid (`100%` of the viewport with a `1150px` floor) rather than a second fixed pixel value, so the content area stays coupled to whatever width the viewport actually provides instead of two independently chosen numbers that could drift apart again on a future pass or a different window size.
2. The 1550px height is derived from measured content, not shrunk to an arbitrary round number: the three-equal-band zone scheme was a fixed constraint (restore Pass B's structure, not redesign it), and real card heights in this dataset run up to 241px, so 1550px is close to the shortest height that avoids row collision under those two constraints together, not a compromise chosen for its own sake.
3. Vertical scrolling past the visible `.canvas-viewport` height was already normal before this pass, since the viewport's own height is a fixed fraction of the browser window regardless of canvas content height; this pass did not attempt to eliminate vertical scroll, only the horizontal scroll and empty sprawl the founder specifically flagged.

## Known limitations, by design

1. The 1150px width floor and 1550px height are tuned against this session's specific dataset (twenty-five stacks, five decks, fifteen top-level canvas items). Adding substantially more items to the seed data in a future pass would need this geometry revisited, the same way it needed revisiting this pass.
2. Everything out of scope for this pass, the deck page, the peek gesture, List and Board rendering, attribution, the marketplace, remains exactly as Pass C left it.
