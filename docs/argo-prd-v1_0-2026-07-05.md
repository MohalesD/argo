## 1. What This Build Produces

By end of day July 7, Argo is a working, multi-user web application a
stranger could use: sign up in seconds, clone a starter QStack, run a
live interview with structured capture and scoring, generate a cited
candidate brief, and share it as a link that turns viewers into users.
This is Kellan's launch-of-friends bar: the full loop works end to end
for real people we invite, with nothing faked along the critical path.

The one-line test for every scope call in this document: does it serve
the loop above? If not, it is specified here but deferred.

## 3. Scope

### 3.1 In scope, fully specified and built

1. Auth, orgs, and membership (multi-user, shared-record from the first
   table).
2. QStacks: creation, editing, cloning, list view, stack view, Kanban
   organization, standard and detail question views, methodology tag.
3. The question bank with retrieval: structured filters plus full-text
   search plus Sonnet re-rank. Provenance and screening status on every
   question.
4. Live interview mode: consent step, question-by-question capture,
   rubric-anchored scoring with audit trail and human override, response
   starring and highlighting, @ mentions.
5. Candidate briefs: Sonnet-drafted, citation-bound to captured
   responses, exportable as PDF (Portable Document Format).
6. Sharing and the PLG (product-led growth) invite loop: tokenized brief
   links, view-without-account, interact-with-account (first name and
   email only), revocable and expiring links.
7. Social layer: public creator profiles (opt-in visibility), short
   posts (280 characters), stars on QStacks, follows, in-app
   notifications.
8. Marketplace, interface only: browse public QStacks, price badges on
   premium listings, a Get button that routes free clones for real and
   shows "Coming soon" for paid.
9. The eval harness and the four eval suites in Section 8, runnable by
   command, with results persisted.

### 3.2 Deferred past July 7, with reasons

1. **Audio capture and transcription (the intelligence layer's capture
   half).** Real-time audio plus speech-to-text is a build of its own,
   and typed capture serves the loop today. The consent step ships now
   anyway (Section 6.3), so audio drops in later without a schema
   change. The candidate brief pipeline is built against captured
   responses, which is the same input transcription will eventually
   produce.
2. **Real payments, creator payouts, commission splitting.** A second
   product's worth of work (processing, fraud, tax handling). Interface
   ships now so the marketplace reads as real; money moves later.
3. **Statistical adverse-impact monitoring dashboards.** Meaningless
   without volume. The structural protections (Section 8.4) ship now;
   the statistics start when real interviews accumulate. Logged as a
   watched item with a trigger: revisit at 500 real scored responses.
4. **Methodology deep-research ingestion at scale.** The methodology
   field and a starter taxonomy ship now; the research pipeline that
   populates it richly is post-window work.
5. **Smaller deferrals:** SMS notifications and the running-late
   notifier, contribution stamps as shareable images (in-app credit
   ships, the image generator does not), email digests, profile display
   fonts, ATS (applicant tracking system) integrations, mobile apps,
   limited-time drops.

## 4. Architecture

### 4.1 Stack

Next.js (App Router) frontend, Supabase for Postgres, auth, row-level
security (RLS), and storage. One repository, one deployment target.
Playwright for end-to-end verification. This mirrors the stack the Ada
build validated three days ago, including the two-user RLS probe
pattern, which transfers directly to Argo's multi-tenant requirement.

### 4.2 The architecture fork, resolved

Argo is greenfield. There is no prior backend; the 2020 capstone repo is
explicitly ruled out as a foundation. The schema is multi-user and
shared-record from the first migration: every domain table carries an
org scope or an explicit public visibility, and RLS enforces tenancy at
the database layer, not the application layer.

### 4.3 Retrieval design

Question retrieval in v1 is structured filtering (role family, level,
category, screening status) plus Postgres full-text search, with Claude
Sonnet re-ranking the top 20 candidates against the interviewer's
context. This is retrieval-based by construction: the model orders and
annotates questions that exist in the bank; it never invents question
text into the result set. Vector embeddings (pgvector) are a stretch
goal, not a dependency; the bank at seed scale (Section 5.4) does not
need semantic search to be useful, and adding an embedding dependency
inside a 36-hour window buys little (decision D6).

### 4.4 Production model routing, structurally enforced

| Call type | Production model |
| --- | --- |
| Question compliance classification | Claude Haiku 4.5 |
| Tag and metadata suggestion | Claude Haiku 4.5 |
| Retrieval re-rank | Claude Sonnet 4.6 |
| In-interview follow-up suggestion | Claude Sonnet 4.6 |
| Candidate brief drafting | Claude Sonnet 4.6 |

Opus is not routed in v1: no production call type needs its depth, and
its latency hurts the live-interview surface. Enforcement is structural,
three layers:

1. Every model call is logged to `ai_calls`, whose `model` column
   carries a CHECK constraint allowing exactly
   `('claude-haiku-4-5', 'claude-sonnet-4-6')`. Adding a model requires
   a migration, which is a deliberate human act. Fable and Mythos
   strings physically cannot be inserted.
2. The application-side model registry is the only path to the API
   client, and it reads from the same allowlist.
3. A test in the hardening pass attempts to log a Mythos-tier call and
   must fail (Section 9, Goal 3).

## 5. Feature Specifications and Acceptance Criteria

### 5.1 Auth, orgs, membership

Magic-link email auth (Supabase). Signup collects first name and email
only, matching the PLG loop's promise. A user creating an account gets a
personal org; they can create additional orgs and invite members by
email with roles owner, admin, member.

Acceptance: a new user reaches a usable workspace in under 60 seconds
from landing; two users in different orgs cannot read each other's
private data (verified by the RLS probe, not by trusting the UI).

### 5.2 QStacks

A QStack is an ordered set of questions, each with a rubric and optional
follow-ups, plus metadata: title, role family, level, methodology,
visibility (private, org, public), and fork lineage. Views:

1. **List view and stack view** over the same data. Stack view renders
   QStacks as card stacks; both support the same actions in the same
   relative positions (Locality-First rule 11, preserved action
   placement).
2. **Kanban organization**: org-defined columns; QStacks move between
   columns by drag and drop with immediate visible confirmation of the
   move and an undo affordance local to the moved card.
3. **Open QStack, standard view**: all questions with rubric and
   follow-ups visible. **Detail view**: a per-question disclosure for
   rationale ("why this question matters") so the standard view stays
   scannable.
4. **Clone**: any public or org QStack clones into the user's workspace
   with lineage recorded (`forked_from_id`), the direct analogue of
   forking a repo.

Acceptance: create, edit, reorder (drag), clone, and Kanban-move all
work with mouse, keyboard, and touch; every mutation shows local
feedback within 200 ms (optimistic) and reconciles on save; a cloned
QStack displays its lineage.

### 5.3 Question bank and retrieval

Every question row carries: text, category (motivation, culture, role,
skill), rationale, provenance (source and author), screening status
(pending, passed, flagged), and verification tier. Search combines
structured filters and full-text; Sonnet re-ranks and annotates the top
20 with a one-line "why this fits" per question.

Two hard rules, enforced in code and covered by evals:

1. Questions with screening status `flagged` never surface in retrieval
   results, interview mode, or public views. They remain visible to
   their author with the flag reason.
2. The re-ranker returns question IDs from the candidate set only.
   Output is validated against input; any ID not in the candidate set is
   discarded and logged.

Acceptance: retrieval fixtures pass the P@5 threshold in Section 8.1;
zero flagged questions appear in any surfaced result across the eval
set; provenance and screening badges render on every question card.

### 5.4 Seed bank

The bank seeds with 300 to 500 questions across 8 to 10 role families,
each passed through the compliance classifier before receiving status
`passed`. Badge language in v1 is **"Screened"**, not "Verified":
screened means it passed the automated compliance eval; verified is
reserved for questions that have also passed an editorial review process
that does not exist yet (decision D14). This keeps the product's central
honesty claim honest on day one.

### 5.5 Live interview mode

Opening a scheduled interview unfurls its QStack into the live surface.
Layout obeys Locality-First as a hard requirement, not a preference: the
active question, the response capture field, the rubric-anchored score
control, star and highlight controls, and the next-question affordance
share one visual neighborhood. No scoring action requires leaving the
answer being scored.

1. **Consent step (blocking).** Before any capture control activates,
   the interviewer confirms that all parties consent to response capture
   and to summarization and sharing with the hiring team. The
   confirmation is stored as a consent record on the session. The
   session state machine has no path from `created` to `capturing` that
   does not pass through `consented` (Section 8.5 tests this).
2. **Capture.** Typed response notes per question, timestamped, with
   star and highlight controls adjacent to the response field.
3. **Scoring.** A 1-to-4 scale with per-question behavioral anchors from
   the rubric, plus a flag control. Not a red/yellow/green verdict
   gauge: anchored scores structure judgment; color verdicts invite
   snap judgment and drift toward automated rejection (decision D9).
4. **AI assistance in-session** is limited to follow-up question
   suggestions drawn from the QStack's follow-up pool, clearly labeled
   as suggestions. The AI never scores a response and never produces a
   hire or no-hire recommendation, in this build or any future one
   without explicit revisiting (Section 8.4).
5. **@ mentions** on a response notify the mentioned org member with a
   deep link that lands on that exact response.

Acceptance: a full mock interview runs start to finish with keyboard
only; every state change (saved, scored, starred, flagged) confirms
visibly at the point of change; the consent gate is unbypassable in the
UI and in the API; a mentioned user's notification lands on the exact
response.

### 5.6 Scoring audit trail and human override

Scores are append-only events. Each row records scorer type (human; the
type `ai` exists in the schema for future capabilities but no v1 code
path writes it), scorer identity, value, anchor, optional rationale, and
timestamp. Corrections and overrides are new rows with
`supersedes_score_id` set; nothing is ever updated or deleted. The
current score is the latest non-superseded row. The full chain renders
in the UI as score history.

Acceptance: overriding a score preserves and displays the original; the
API rejects UPDATE and DELETE on score rows (enforced by RLS policy and
covered by a test).

### 5.7 Candidate briefs

On session end, Sonnet drafts a brief structured as: role context,
per-category summaries, starred moments, and open questions. Every
factual claim about the candidate carries a citation to a specific
captured response ID, rendered as an expandable reference. Claims that
cannot be grounded in a captured response do not survive the generation
pipeline (Section 8.3 enforces this). The interviewer reviews and can
edit before the brief is markable as final. PDF export renders the same
content server-side.

Acceptance: on the eval transcript set, zero unsupported claims; every
citation resolves to a real response; edit-then-finalize works; the PDF
matches the web brief.

### 5.8 Sharing and the PLG invite loop

A finalized brief can be shared by tokenized link. The recipient sees
the brief without an account. Any interaction (commenting, saving,
starring) prompts account creation with exactly first name and email:
"Kathy invited you to view the candidate responses. Create a free
account in five seconds to view." Links carry a default 30-day expiry
and are revocable by the sharer; both controls sit on the share dialog
itself, next to the link they govern (candidate briefs contain a real
person's data; expiry and revocation are the minimum responsible
handling, decision D13). Invite conversion (link view to account
created) is instrumented.

Acceptance: view-without-account works; interaction gates correctly;
revoked and expired links show a respectful dead-end page that does not
leak brief content; conversion events record.

### 5.9 Profiles, posts, stars, follows, notifications

Profiles carry handle, display name, bio, avatar, and a visibility
toggle, default private, prompted to public on first public QStack
(decision D12). Posts cap at 280 characters. Stars are one per user per
QStack, with cached counts on QStack cards. Following a creator
subscribes to their releases: publishing a public QStack notifies
followers in-app. Contribution credit: when a user's question is
accepted into the shared bank, they receive an in-app credit
notification and a permanent attribution line on the question.

Acceptance: star counts are correct under concurrent starring; follows
produce notifications on publish; a private profile is unreachable by
URL guessing (RLS-verified).

### 5.10 Marketplace, interface only

Public QStack browsing with sort by stars and recency. Premium listings
render price badges and a Get button that shows "Coming soon"; free
public QStacks clone for real through the same surface. The listing
schema (price, status) ships now so payments later is a feature
addition, not a migration.

Acceptance: free clone path works end to end; no code path can take
payment or promise delivery of a paid item.

## 6. Data Model

Every table carries `id`, `created_at`. Tenancy: org-scoped tables carry
`org_id` under RLS; public visibility is explicit, never default.

1. `orgs` (name)
2. `users` (email unique, first_name)
3. `org_members` (org_id, user_id, role in owner/admin/member)
4. `profiles` (user_id, handle unique, display_name, bio, avatar_url,
   visibility in private/public)
5. `posts` (author_id, body, 280-char check)
6. `follows` (follower_id, followee_id, unique pair)
7. `qstacks` (org_id, owner_id, title, role_family, level, methodology,
   visibility in private/org/public, forked_from_id nullable,
   star_count cached)
8. `questions` (text, category, rationale, provenance jsonb,
   screening_status in pending/passed/flagged, verification in
   screened/verified, contributed_by nullable)
9. `qstack_items` (qstack_id, question_id, position, rubric jsonb,
   followups jsonb)
10. `kanban_columns` (org_id, name, position) and `qstack_positions`
    (qstack_id, column_id, position)
11. `stars` (user_id, qstack_id, unique pair)
12. `interviews` (org_id, qstack_id, candidate_name, candidate_email
    nullable, role, scheduled_at, status)
13. `interview_sessions` (interview_id, state in
    created/consented/capturing/ended, started_at, ended_at)
14. `consents` (session_id, party in interviewer/candidate/other,
    method, consented_at, recorded_by)
15. `responses` (session_id, question_id, response_text, starred bool,
    highlights jsonb, created_by)
16. `scores` (response_id, scorer_type in human/ai, scorer_id, value
    1-4 check, anchor, rationale, supersedes_score_id nullable;
    append-only via RLS: no UPDATE, no DELETE)
17. `mentions` (response_id, mentioned_user_id, author_id)
18. `briefs` (interview_id, content jsonb with per-claim citation
    response IDs, generated_by_model, status in draft/final)
19. `brief_shares` (brief_id, token unique, created_by, expires_at,
    revoked_at nullable)
20. `invites` (share_id, accepted_user_id nullable, accepted_at)
21. `notifications` (user_id, type, payload jsonb, read_at nullable)
22. `marketplace_listings` (qstack_id, price_cents, status in
    preview_only)
23. `ai_calls` (purpose, model CHECK in allowlist, tokens_in,
    tokens_out, cost_usd)
24. `eval_runs` (suite, model, passed bool, metrics jsonb, ran_at)

## 7. Design System Anchors

Palette (extrapolate shades from these anchors; every text-on-background
pairing meets WCAG (Web Content Accessibility Guidelines) AA):

1. Primary gold `#E3A81C` with hover `#C9971A`: bright, immediately
   legible as gold. Reserved for primary actions, stars, and moments of
   accomplishment, not for body surfaces.
2. Surfaces: white `#FFFFFF` and light cream `#FBF6E9`, generous use.
3. Body text: dark warm gray `#2B2A26`; secondary text `#55524A`.
4. Dark forest green `#2E4A3A`: minor accent only (screening badges,
   subheads, success states).
5. Flag and destructive: a warm red family, used sparingly.

Type: a distinctive serif for headings, a highly readable sans for body
and UI (the working pairing from the documentation set, Source Serif 4
and Inter, carries over until Claude Design's guidelines land; the
system is structured so those drop in without rebuild).

Interaction: Locality-First doctrine, full text in the project files,
compressed 15 rules in its Section 21, applied as the review checklist
for every surface. Microcopy follows the no-blame framework: what
happened, what to do next, is your work safe; labels name outcomes.

## 8. Evals and the Workday Lesson

The design lesson from the ongoing Workday AI-hiring discrimination
litigation (Mobley v. Workday): when an automated tool screens, scores,
or ranks candidates, courts are willing to treat the tool's operator as
an agent of the employer, and disparate impact claims attach to the
algorithm's behavior even without discriminatory intent. Litigation
status will keep evolving; the design posture does not depend on the
outcome. Argo's posture, structural rather than aspirational:

**8.1 Retrieval quality suite.** 25 role-and-level query fixtures with
human-judged relevant sets. Threshold: precision at 5 of at least 0.6,
and zero flagged questions in any result. Run on every change to
retrieval code or the seed bank.

**8.2 Compliance screening suite.** A labeled set of roughly 60
questions spanning safe, risky, and illegal (protected-characteristic
probes: age, family status, national origin, disability, religion, and
adjacent proxies). Threshold: recall of 1.0 on the illegal class within
the eval set (no illegal question labeled safe), with flagged-class
precision reported and tuned. The classifier gates `screening_status`;
nothing enters `passed` without passing here.

**8.3 Brief faithfulness suite.** 15 synthetic interview transcripts
with known ground truth. Threshold: zero unsupported claims; every
factual sentence in a generated brief cites a response ID that exists
and supports it. A brief that fails regenerates with tighter grounding;
persistent failure blocks the finalize action, never silently ships.

**8.4 Adverse-impact posture, structural in v1.** Argo's AI does not
score candidates, does not rank candidates, does not recommend hire or
no-hire, and does not infer protected characteristics. Humans score
against behavioral anchors; the AI structures, retrieves, and
summarizes with citations. Every scoring event is attributed and
overridable with full history. This is the property that makes the
Workday failure mode structurally unavailable rather than merely
discouraged. Statistical adverse-impact monitoring begins at the
500-scored-responses trigger (Section 3.2.3).

**8.5 Consent enforcement test.** Automated: an interview session
cannot reach `capturing` without a consent record, attempted via UI
path and direct API call; both must fail.

Eval results persist to `eval_runs`. The build log records thresholds
chosen and any tuning.

## 9. Build Sequencing for the Window

Three sequential goals with a real checkpoint between each, per the
validated Ada pattern. Each goal: named files read first, explicit
scope boundary, reuse mandates, autonomous operation, a build log
written as the run proceeds (human-readable plus JSON), a concrete
definition of done, and a turn cap so an unresolvable run reports back
instead of spinning.

1. **Goal 1, backbone.** Schema and migrations with RLS, auth, orgs,
   the ai_calls constraint, seed bank ingestion with compliance
   screening, eval harness with suites 8.2 and 8.5 green. Done when:
   two-user RLS probe passes, a Mythos-tier insert into ai_calls fails,
   seed bank is queryable with badges.
2. **Goal 2, surfaces.** QStack library (list, stack, Kanban, clone),
   retrieval with re-rank, live interview mode with consent gate and
   scoring, briefs with citations and PDF, share loop, profiles, stars,
   follows, notifications, marketplace interface. Done when: the full
   launch-of-friends loop passes as a scripted Playwright run.
3. **Goal 3, hardening.** Suites 8.1 and 8.3 green, keyboard and touch
   parity pass on the interview surface, empty states and error states
   to the microcopy standard, the "could not verify" section of the
   build log reviewed and each item either verified or explicitly
   accepted, cost review of ai_calls.

Checkpoint discipline between goals: the three-sentence test on each
new component, and a read of the decisions table in the build log
before the next goal fires.

1. The launch-of-friends loop passes end to end via Playwright: signup,
   clone, interview with consent, score with override, brief with
   citations, share, second account created through the link, star and
   follow.
2. All five eval suites green at their thresholds, results in

## 11. Risks and Watched Signals

1. **The GitHub-mechanic transfer assumption.** Stars, follows, and
   public profiles bet that a developer-culture virality loop transfers
   to HR professionals. Untested. Watch invite conversion and
   star-per-viewer rates from the first real users; do not build deeper
   social mechanics until these move.
2. **Seed bank quality bottleneck.** 300 to 500 screened questions is
   an aggressive editorial lift inside the window. Mitigation: generate
   candidates in bulk, screen automatically (8.2), and let Mo spot-check
   by role family; the "Screened" badge language (D14) keeps claims
   honest at whatever depth review reaches.
3. **Brief links carry candidate PII (personally identifiable
   information).** Mitigated by default expiry, revocation, and
   no-content dead ends; full data-subject tooling (export, delete) is
   post-window and pre-real-users, on Nadia's desk.
4. **Tier-4 autonomous interview agents** stay a watched market signal,
   not a target, for Jordan's and Nadia's independently sufficient
   reasons already logged in the persona master.
